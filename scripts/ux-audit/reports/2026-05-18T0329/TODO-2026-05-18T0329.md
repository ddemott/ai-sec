## Follow-ups from done items (spawned 2026-05-18)

- [ ] **#10-followup · P2 · S — Wire `/` to focus the active tab's search input**
  Deferred from #10 because focusing a tab-specific input from the global keyboard layer requires per-tab DOM coordination. Two viable approaches: (a) every search-bearing view dispatches a `ai-sec:focus-search` listener that calls `.focus()` on its `<input>`, mirroring how `N` already works; (b) standardize on a `data-shortcut-target="search"` attribute and have the hook walk the DOM for the first match. Either is small (~30 lines).
  - `dashboard/lib/useKeyboardShortcuts.ts` — register `/`
  - Consumers: `CRMView.tsx` (customer search), `KnowledgeBaseView.tsx` (KB doc search), `BusinessTypePicker.tsx` (template search)
  - New help-modal row: `/  Focus search`

- [ ] **#7-followup · P2 · M — Migrate MyBusinessView + FirstRunTour to `useOnboardingState`**
  The reducer landed for DashboardHome in `b1d33dd`. Two more consumers still maintain their own gating:
  - `dashboard/components/MyBusinessView.tsx:107–134` — has the same welcome → chooser → picker → wizard fork, duplicated locally
  - `dashboard/components/FirstRunTour.tsx` — separate localStorage flag; sits alongside the wizard
  Migrating MyBusinessView is the bigger win because the duplicated flag matrix is the exact risk #7 was about. FirstRunTour is one-off enough that leaving it on a localStorage flag is reasonable — but should at least co-exist correctly with the reducer (assert that `tour` doesn't render while `welcome/chooser/picker/wizard` does). Add a `stage === 'tour'` to the enum if doing this properly.
  - Extend `lib/useOnboardingState.ts` with a `tour` stage if including FirstRunTour
  - Refactor MyBusinessView's wizard fork
  - Extend the existing test (`lib/useOnboardingState.test.tsx`) with tour-vs-wizard exclusivity
