### [2026-06-02] process — Wizard pre-fill from business template

**Target:** `dashboard/` onboarding wizard + `src/templates/`
**Category:** process
**Priority:** low (demoted 2026-06-10 — subordinated to Website Knowledge Import)
**Effort:** M (30min–2hr)
**Status:** approved (re-parented as tier 3 of the Website Knowledge Import precedence)

**Re-prioritization (2026-06-10):** This is NOT the primary onboarding pre-fill. Per the answer-precedence decision (owner-confirmed > scraped-from-their-site > industry-template default > blank), the industry template is **tier 3 — the fallback floor** beneath the Website Knowledge Import feature (`docs/superpowers/specs/2026-06-09-website-knowledge-import-design.md` §4a). The owner's own website is ground truth; the template only fills gaps the site + owner haven't supplied. **Scoped:** the floor applies ONLY to generalizable questions (policy/vocab), NEVER to tenant-specific operational facts (hours, address, phone, prices, staff — those stay blank + flagged). Build as a sub-component of the website feature, not standalone. Website Knowledge Import (Plans 1→2→3) is the priority.

**Proposal:**
When a new tenant selects a business type during onboarding (e.g., "Hair Salon"), the wizard should pre-populate every form field with values from the matching YAML template (`salon_v1`, `automotive_v1`, etc.). The user reviews, tweaks their specific details (name, hours, address), and confirms — one tab-through instead of a blank form. Currently templates apply data to the DB after the wizard but fields are blank during entry.

**Rationale:**
Templates exist but the UX doesn't realize their value — users still type everything from scratch. Pre-fill turns a 20-minute setup into a 2-minute review. Bella's Hair Studio in the seed serves as the reference dataset for building and testing this flow.

**Implementation note (2026-06-02, approved):** real effort is L, not M. This IS the SetupWizard draft-state rework already scoped in [docs/TODO.md](TODO.md) → "`SetupWizard` + `SoloWizard` draft state" (Phase B): hold services/resources/employees/shifts/mappings in local state, pre-fill from the matching YAML template, commit to DB only on the Step 7 Done click, discard on dismiss. Touches `useWizardCrud.ts` + every `Step*.tsx` + ~5 test files (~5K lines); needs `VocabularyProvider` to accept an `overrideTemplate`. **Open on a fresh branch in a dedicated session.** Preserve the auto-seed-rollback contract in `dashboard/components/SetupWizard/SetupWizard.backToPicker.test.tsx`.

### [2026-06-10] refactoring — Split the 1398-line agentTools.ts route module

**Target:** `src/routes/agentTools.ts`
**Category:** refactoring
**Priority:** medium
**Effort:** L (>2hr)
**Status:** proposed

**Proposal:**
`agentTools.ts` is 1398 lines — ~1.6× the next-largest production route (`versionHistory.ts` 851, `appointments.ts` 638) and the clear outlier in `src/routes/`. It bundles 13 `toolRoute()` tool handlers + 2 `_test/sync-events` endpoints + shared helpers (`ok`/`fail`/`toolRoute`/`parseOrFail`/`bookingOutcomeFromAgentError`) + a block of pure interval-math helpers at the bottom (`timeToMinutes`, `dateTimeToMinutes`, `minutesToTime`, `mergeIntervals`, `subtractIntervals`). Natural seams to split along: (1) the shared helpers → a small `agentTools/helpers.ts`; (2) the interval math → its own util (and cross-check for overlap with `shared/scheduling.ts` before duplicating); (3) group the handlers by concern — booking (`book-appointment`, `book-with-scheduling`, `scheduling-options`, `available-slots`, `check-availability`), customer/preference (`customer-context`, `save-customer-preference`, `service-catalog`, `tenant-config`, `policy-answer`), phone verification (`send-verification-code`, `verify-phone-code`). Keep `toolRoute`'s metrics/outcome wiring intact. Done = no single file >~600 lines, each module owns one concern, and all 99 agent tests + Playwright e2e stay green. Per CLAUDE.md's "working flat code beats a dormant abstraction," this is a true size-driven split, not speculative layering.
